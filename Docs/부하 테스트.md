## 테스트 환경

| 구분 | 사양 |
| --- | --- |
| **Server** | AWS EC2 c6i.4xlarge (16 vCPU, 32GB RAM) x 1대, Windows Server 2022 |
| **Client** | AWS EC2 c6i.xlarge (4 vCPU, 8GB RAM) x 4대, Windows Server 2022 (각 2,500봇 = 총 10,000봇) |
| **Network** | 동일 리전, 동일 클러스터 배치 그룹 (Cluster Placement Group) |
| **채팅 시나리오** | 로그인 → 방 입장 → 채팅(3~5초 간격, 평균 4초) → 퇴장 → 재입장 반복 |
| **스레드 구성** | 시나리오별 조정 필요 — [권장 스레드 표](#시나리오별-권장-스레드-구성-16-vcpu-기준) 참조 |


| **테스트 모드** | `TestMode=true` — Redis/MySQL I/O 우회, 순수 엔진 성능 측정 |

> Scenario A(스레드 황금 비율)는 4-core c6i.xlarge에서 측정한 과거 데이터로, 환경이 다르므로 본문에 별도 표기했습니다.

## 10,000명 수용량 테스트 및 Zero-Leak 검증

c6i.xlarge 클라이언트 4대(각 2,500봇)로 10,000명의 더미 클라이언트가 실제 유저와 동일한 시나리오(로그인 → 방 입장 → 채팅 → 방 퇴장 → 재입장)를 3~5초 간격으로 반복하는 연속 부하 테스트를 수행했습니다. 결과는 **100방 × 100명** 구성 기준입니다.

### 1. 클라이언트 부하 테스트 지표

| 측정 항목 | 결과 수치 | 상태 요약 |
| --- | --- | --- |
| **최대 동시 접속 (Peak Conn)** | **10,000 명** | 목표 수용량 달성 |
| **연결 실패 / 끊김** | **< 2 건 / 10,000** | 사실상 세션 유실 0 |
| **평균 지연 시간** | **17.55 ms** | 실시간 통신 수준 유지 |
| **p99 지연 시간** | **~17ms** (순간 최대 744ms) | 100방 × 100명, 99%의 초에서 17ms 이하 |
| **수신 처리량** | **134K pkts/s** (broadcast ops/s ~143K) | CPU 33%, 헤드룸 충분 |
| **이상 현상** | **없음** | 무중단 서비스 검증 완료 |

### 2. 서버 안정성 검증

| 서버 내부 지표 | 측정 값 | 의미 |
| --- | --- | --- |
| **메모리 점유** | **394 MB 고정** | 장기 운용 중 변동 없음 (누수 0) |
| **SendPool Alloc Fail** | **0 회** | 전 테스트 구간(1차~5차) 누적 |
| **JobPool Alloc Fail** | **0 회** | Pool 고갈 없이 안정 순환 |
| **연결 실패** | **< 2 건 / 10,000** | TCP 핸드셰이크 단계 일시적 실패 추정 |

### 3. 트러블슈팅: OS 레벨 교차 검증을 통한 Zero-Allocation 증명

서버 내부 지표(Pool Free Count = 전량 반환)로 객체 누수가 없음을 확인한 뒤, AWS CloudWatch와 VS 프로파일러를 통한 OS 레벨 메모리 모니터링으로 교차 검증했습니다.

#### Phase 1: 실제 메모리 누수 발견 및 수정

- **현상**: 최초 10,000명 테스트에서 서버 메모리가 **99%(6,680MB)** 를 점유하며 **0.4MB/s** 씩 지속 증가
- **원인 분석**:
    1. **SendBuffer Pool 과잉 할당**: 봇당 400개씩 총 4,000,000개 할당 → 약 4.1GB 낭비
    2. **세션 버퍼 비대화**: `MAX_PACKET_DATA_BUFFER_SIZE`가 65,536으로 과도하게 설정
    3. **세션 종료 시 리소스 미반환**: `Closed()`에서 `Clear()` 미호출로 Send큐 잔존
- **해결**:
    1. Pool 크기를 봇당 **400 → 10**으로 최적화
    2. 버퍼 크기를 **65,536 → 8,192**로 조정
    3. `Closed()` 호출 시 `Clear()`로 세션 리소스 즉시 반환
- **결과**: 0.4MB/s 누수 해소, 16-core 환경 재측정에서 메모리 **394MB 고정**으로 안정화

#### Phase 2: OS 레벨 교차 검증을 통한 Zero-Leak 최종 증명

- **현상**: Phase 1 수정 후 메모리가 안정화되었으나, 10,000명 접속 해제 후에도 메모리가 떨어지지 않는 현상 발견
- **프로파일링**: VS 프로파일러 힙 스냅샷(Heap Snapshot)으로 분석. 10,000명 접속 전/후 스냅샷을 비교한 결과, 할당된 메모리의 증가량은 **+0 Bytes**
- **결론**: Lock-Free Object Pool이 해제된 세션/버퍼를 OS에 반납하지 않고 다음 접속을 위해 캐싱(Pre-allocation)하고 있었음. C++ CRT 힙 할당자의 정상 동작.
- **최종 성과**: 1만 명의 유저가 장시간 통신을 주고받는 환경에서도, 추가적인 동적 할당 없이 **394MB의 고정 메모리**로 무중단 서비스가 가능함을 확인

## Scenario A: 스레드 황금 비율 (4-core c6i.xlarge)

> 본 시나리오는 **4-core c6i.xlarge 환경**에서 측정된 데이터입니다. 16-core c6i.4xlarge 권장값은 본 섹션 끝에 별도로 정리되어 있습니다.

4코어 환경에서 IO Worker / Logic Thread 조합을 바꿔가며 최적 비율을 실측했습니다.

#### 저부하 (방당 8명, 채팅 여유)

| 테스트 | 설정 (MaxIOWorkerThread/MaxWorkerThread/MaxLogicThread) | 평균 레이턴시 | p99 | CPU |
|--------|--------------------------|-------------|-----|-----|
| A-1 | IO4 / W2 / L2 (총 4개) | 16.10 ms | 32.13 ms | 32.41% |
| A-4 | IO4 / W4 / L2 (총 6개) | 15.69 ms | 32.77 ms | 35.49% |
| A-3 | IO4 / W2 / L4 (총 6개) | 15.89 ms | 23.01 ms | 22.15% |
| **A-2** | **IO4 / W2 / L4 (총 6개)** | **15.89 ms** | **17.21 ms** | **22.22%** |

> Logic Thread 2개(A-1, A-4)는 p99가 32ms로 불안정. **Logic Thread 4개가 핵심.**

#### 고부하 (방당 8명, 채팅 집중)

| 테스트 | 설정 (MaxIOWorkerThread/MaxWorkerThread/MaxLogicThread) | 평균 레이턴시 | 수신 TPS | CPU |
|--------|--------------------------|-------------|---------|-----|
| A-1 | IO4 / W2 / L2 | 251 ms | 146,277 pkts/s | 94.87% |
| **A-2** | **IO4 / W2 / L4** | **261 ms** | **128,528 pkts/s** | **87.38%** |
| A-3 | IO4 / W4 / L2 | 294 ms | 120,565 pkts/s | 100% |
| A-4 | IO8 / W4 / L4 | 401 ms | 91,093 pkts/s | 99.82% |

> A-4는 스레드가 가장 많지만 최악. 4코어에 Worker(4)+Logic(4)=8 스레드는 2배 오버서브스크립션 → 컨텍스트 스위칭 폭증.
> **4-core 최적 비율: IO4 / W2 / L4** — CPU 87%로 유일하게 헤드룸 확보, 저부하 p99 17ms.
> 4-core 한정 엔진 물리 한계는 **수신 TPS ~118,000 pkts/s** (방당 1,000명 브로드캐스트 환경 별도 측정에서 확정).

#### 16-core c6i.4xlarge 권장값

본 환경에서는 단계별 부하 시험(Scenario B, 1차~5차)을 통해 **시나리오별로 스레드 비율을 조정해야 한다**는 결론을 도출했습니다. 방 인원이 많으면 IOCP Worker에 코어를 집중하고, 방 수가 많으면 Logic Thread에 코어를 집중합니다. 상세 권장값은 [Scenario B의 시나리오별 권장 스레드 구성](#시나리오별-권장-스레드-구성-16-vcpu-기준)을 참조해 주십시오.

## Scenario B: 부하 단계별 한계 탐색 (16-core c6i.4xlarge)

방 인원과 방 개수의 조합을 바꿔가며 권장 운영점과 절대 한계를 탐색했습니다. 채팅 간격은 모두 3~5초(평균 4초)로 동일합니다.

### 실측 결과 (고정 스레드 구성: Worker=8, IOWorker=8, Logic=4)

| 구성 | CPU | Latency Avg | p99 | Broadcast ops/s | 비고 |
| --- | --- | --- | --- | --- | --- |
| 200방 × 50명 | **50%** | **20.73 ms** | ~32ms (최대 1,310ms) | **~288K** | 안정 영역 |
| 500방 × 20명 | **90%** | **49.24 ms** | ~156ms (최대 344ms) | **~884K** | IOCP 포화 구간 |
| 1000방 × 10명 | 100% | 11+ s | 36+ s | — | Logic Thread 부족으로 성능 급락 |

> 이 결과는 I/O 편향(Worker=8) 구성에서 측정한 값이며, Strand 비중이 높은 1000방×10명 환경에서는 Logic Thread(4개) 부족으로 인해 성능이 급락했습니다.
> 시나리오에 따라 스레드 비율을 적절히 조정해야 합니다.

### 시나리오별 권장 스레드 구성 (16 vCPU 기준)

방 인원이 많으면 I/O(WSASend fan-out)가 병목이 되고, 방 수가 많으면 Logic(Strand 스케줄링)이 병목 지점이 됩니다. 따라서 **고정된 스레드 구성에 절대적으로 적합하거나 부적합한 시나리오는 없으며, 시나리오의 성격에 맞게 스레드 비율을 유연하게 조정해야 합니다.**

| 시나리오 | 병목 | MaxWorkerThread | MaxIOWorkerThread | MaxLogicThread |
| --- | --- | :-: | :-: | :-: |
| 10방 × 1000명 | IOCP Worker (fan-out 999×) | **12** | **12** | **2** |
| 50방 × 200명 | IOCP Worker (fan-out 199×) | **10** | **10** | **4** |
| 200방 × 50명 | 균형 | **8** | **8** | **6** |
| 500방 × 20명 | Logic Thread (500개 방 큐) | **6** | **6** | **8** |
| 1000방 × 10명 | Logic Thread (1000개 방 큐) | **4** | **4** | **10** |

> 원칙: Worker + Logic <= 14 (16 vCPU에서 OS 및 기타 시스템 여유 자원 2개를 제외합니다). 방 인원이 많으면 IOCP Worker에 코어를 집중 배치하고, 방 수가 많으면 Logic Thread에 코어를 집중 배치합니다.

### 단계별 측정치 (1차~5차)

| 차수 | 방 구성 | CPU | Latency Avg | p99 | Recv/s | Broadcast ops/s |
| --- | --- | --- | --- | --- | --- | --- |
| 1차 | 100명 × 100room | — | 23.50 ms | ~17ms (최대 1,902ms) | 127K | ~143K |
| 2차 | 100명 × 100room | — | 17.93 ms | ~17ms (최대 748ms) | 140K | ~143K |
| 3차 | 100명 × 100room | 33% | **17.55 ms** | **~17ms (최대 744ms)** | 134K | ~143K |
| 4차 | 200명 × 50room  | 50% | **20.73 ms** | ~32ms (최대 1,310ms) | 235K | **~288K** ✅ |
| 5차 | 500명 × 20room  | 90% | **49.24 ms** | ~156ms (최대 344ms) | 417K | **~884K** ⚠️ |

> 1 ~ 3차는 동일 구성(100×100)에서의 반복 측정으로, 측정 환경 안정화 후 3차를 대표값으로 채택했습니다.
> 4차에서는 방 개수를 2배(50→200)로, 방당 인원을 절반(50→1/2)으로 조정한 결과, **broadcast ops/s가 약 2배** 증가했으나 CPU 점유율은 50%를 유지했습니다. 이를 통해 Strand 병렬도가 처리량을 결정하는 지배적 요인임을 확인했습니다.
> 5차에서는 방 개수를 500방으로 더욱 늘린 결과, p99 중앙값이 ~ 156ms로 올라갔으나(CPU 90% 포화) 최대 스파이크는 344ms로 억제되었습니다. 이는 Strand 단위가 작아져 직렬화 큐가 짧게 유지된 결과입니다.
> **p99 표기 방식**: `~Xms (최대 Yms)` 형식은 "초당 p99의 중앙값 (전체 구간 최대 순간 스파이크)"를 의미합니다. 1 ~ 3차의 최대 스파이크(744 ~ 1902ms)는 전체 측정 시간 중 1 ~ 2초간만 발생한 이상치이며, 99% 이상의 시간에서 p99는 17ms 이하로 안정적이었습니다.

### 보조 데이터: 1000방 × 10명 (고정 구성 Worker=8, Logic=4)

| 구분 | 방 구성 | 환경 | CPU | Latency Avg | p99 | Recv/s |
| --- | --- | --- | --- | --- | --- | --- |
| 보조 A | 1000 × 10 | c6i.xlarge | ~100% | 11,435 ms | 36,066 ms | 128K |
| 보조 B | 1000 × 10 | c6i.4xlarge | ~80% | 4,202 ms | 5,741 ms | 555K |

> 보조 A와 B 환경 모두 평균 지연시간이 초 단위로 급증했습니다. 이는 1000개의 방 큐를 Logic Thread 4개가 처리하는 구조에서 **Strand 스케줄링 오버헤드**가 병목으로 작용한 결과입니다.
> 4xlarge 인스턴스로 스케일업(16 vCPU)할 경우 지표는 일부 개선되지만, 근본적인 해결책이 되지는 못합니다.
> **Logic Thread를 10개로 증가시킬 경우(권장 스레드 표 참조) 성능이 개선될 수 있으며, 이는 추가적인 검증이 필요합니다.**
> 대형 방 지원을 위한 구조적 개선 방안은 [향후 개선 방향](../README.md#향후-개선-방향)의 "Room Sharding (대형 방 분할)" 항목에서 논의합니다.
