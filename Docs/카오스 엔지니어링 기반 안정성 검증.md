# 카오스 엔지니어링 기반 안정성 검증

Lock-Free 아키텍처와 Strand 패턴의 무결성을 검증하기 위해, 자체 제작 Chaos Bot System으로 4단계 스트레스 테스트를 진행했습니다. 단순한 처리량(TPS) 측정을 넘어, Lock-Free의 주요 취약점(ABA, Data Race, 좀비 세션, 라우팅 경계 경쟁)에 대한 방어 로직을 테스트 범위 내에서 검증했습니다.

## 4대 시나리오 검증 요약

| 시나리오 | 테스트 내용 | 결과 |
|----------|-----------|------|
| **A. ABA 오버플로우 방어** | 30분간 771,438회 RST 강제 재접속 사이클 반복 | 메모리 오염 및 Crash 0건 |
| **B. Strand Race 방어** | 공유 자원(Room) 동시 접근 버스트 81회 반복 | Data Race 0건 |
| **C. 좀비 및 단편화 공격** | 1바이트 단편화 전송 + RST 강제 종료 285회 | 조립 에러 0건, 좀비 세션 잔류 0건 |
| **D. Fast Path 라우팅 경계** | 26,326회 LeaveRoom+Chat 동시 전송으로 경쟁 조건 유발 | 서버 Crash 0건, 실질 데이터 손실 0건 |

## Scenario A: Lock-Free 메모리 무결성 및 ABA 오버플로우 검증

- **Test:** 950개 봇이 30분간 RST 강제 종료 + 즉시 재접속(Gen Pump)을 **771,438회** 반복하며 Lock-Free Object Pool의 세션 슬롯 재사용을 극한까지 스트레스 테스트.
- **Result:** `ABA Overflow 0건`, `서버 크래시 0건`, `Gen Pump 사이클 771,438회 완료`
- **Insight:** Lock-Free Object Pool의 ABA 문제를 **Generation(세대) 검증과 RefCount(참조 카운트) 기반의 안전한 메모리 반납 로직**으로 방어. 로그인 실패(856,223건)는 ReuseSessionWaitTimeSec 슬롯 대기 중 재접속 시도에 대한 정상적인 거부 동작으로, 서버가 부하 아래에서도 상태를 일관되게 유지함을 확인.

## Scenario B: Multi-Thread 논리적 경합 (Strand Race) 검증

- **Test:** 100개의 봇이 동시다발적으로 방 입장/퇴장 및 채팅 도배 요청을 81회 반복(Pipeline Burst)하며 공유 자원(Room)에 대한 Data Race를 유발. Room Enter 220회 시도 중 39회 실패(비정상 상태 전이 요청)를 포함.
- **Result:** `Strand Race 0건`, `비정상 패킷 차단(Fail) 확인`
- **Insight:** 수백 개의 스레드가 동일한 Room 자원에 동시 접근하려 했으나, StrandProcessor를 통한 작업 직렬화(Serialization)가 동작하여 동기화 오류를 방지. 비정상적인 상태 전이 요청(Enter Fail 39건)은 입구에서 즉시 차단하여 서버 로직을 보호.

## Scenario C: 악성 네트워크 공격 및 좀비 세션 검증

- **Test:** 모든 통신 패킷을 1바이트 단위로 조각내어 전송(TCP 단편화)하고, 정상 통신 중 강제 RST(Hard Close)를 285회 반복 시도. Chat Sent 5,700건을 포함한 총 6,293개 패킷 전송.
- **Result:** `Zombie Race 0건`, `패킷 조립 에러 0건`, `서버 크래시 0건`
- **Insight:** 1바이트 단위 TCP 단편화 테스트에서도 RingBuffer의 패킷 경계 파싱 로직이 정상 동작. RST 강제 종료(285건) 및 예상치 못한 연결 해제(247건) 발생 시 `CancelIoEx`와 내부 Task Queue를 활용한 좀비 세션 정리(Cleanup) 로직이 정상 작동. 테스트 과정에서 **힙 손상(0xC0000374) 버그를 발견 및 수정**하였으며, 발견하지 못했다면 프로덕션에서 잠재적 크래시로 이어졌을 실제 취약점이었음.

  **발견된 버그: ZOMBIE_CLEANUP 핸들러의 잘못된 `delete` 호출**

  리팩토링 과정에서 `ClientSession.cpp`의 `mZombieContext`를 `new` 힙 할당에서 멤버 변수로 전환했으나, `IOCP.cpp`의 ZOMBIE_CLEANUP 핸들러에서 해당 `delete` 호출을 제거하지 않음.

  ```cpp
  // IOCP.cpp — 수정 전 (버그)
  else if (IOOperation::ZOMBIE_CLEANUP == op)
  {
      CloseSocket(pClientSession);
      delete reinterpret_cast<stOverlappedEx*>(lpOverlapped);  // ← 멤버 변수를 delete
      ...
  }
  ```

  `lpOverlapped`는 `&pClientSession->mZombieContext`(스택/멤버 변수)의 주소인데, 힙 포인터가 아닌 주소에 `delete`를 호출하여 힙 메타데이터가 즉시 손상됨. 이후 `ReleaseRef()` 호출 시점에 `0xC0000374` 크래시로 표면화.

  ```cpp
  // IOCP.cpp — 수정 후
  else if (IOOperation::ZOMBIE_CLEANUP == op)
  {
      CloseSocket(pClientSession);
      // delete 제거 — mZombieContext는 멤버 변수이므로 자동 소멸
      ...
  }
  ```

## Scenario D: Fast Path 라우팅 경계 검증

- **Test:** 200개 봇이 60초간 `ROOM_LEAVE_REQUEST` 직후 즉시 `CHAT`을 전송하여, IOCP Worker(Fast Path)와 ProcessThread(Slow Path)의 라우팅 경계 경쟁 조건을 **26,326회** 유발.
- **Result:** `서버 Crash 0건`, `Hard Close 0건`, `Routing Boundary Drops 4~6건`
- **Insight:** Fast Path와 Slow Path 경계에서 Chat이 LeaveUser 이후 Room에 도달하는 경우, 서버가 "Invalid room number" 로그 후 graceful drop으로 방어(크래시·연결 종료 없음). 4~6 drops는 서버 버그가 아닌 **60초 강제 종료 시 ROOM_LEAVE_SENT 상태인 봇의 통계적 타이밍 artifact**임을 `botsPerRoom=1` 격리 테스트로 확인.
