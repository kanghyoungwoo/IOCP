# 연산 경로 지연 측정

패킷 수신 완료부터 송신 큐 적재(WSASend 직전) 까지, 네트워크 I/O를 제외한 순수 연산
경로의 지연을 나노초 단위로 실측한 기록입니다. 

측정 대상 경로:

```
[Producer]  링버퍼 framing → Job 할당 + 262B 본문 복사 → 방 MPSC 큐 적재 → GlobalQueue push
[Consumer]  GlobalQueue pop → 방 Strand 처리 → 브로드캐스트 → 세션별 송신 큐 적재
```
측정에 포함한 것과 뺀 것:

| ✅ 포함 | ❌ 제외 |
|---|---|
| 링버퍼 framing / 패킷 파싱, 세대 검증 | NIC · 커널 TCP 스택 |
| Job 풀 할당 + 본문 복사 | `WSASend` 시스템 콜 |
| 락프리 큐 적재/취득 (MPSC, MPMC) | 클라이언트 왕복(RTT) |
| 방 Strand 처리 + 브로드캐스트 큐 적재 | DB/Redis 연동 경로 |

---

## 1. 핵심 결과

**환경**: AWS EC2 c6i.4xlarge · Intel Xeon Platinum 8375C @ 2.90GHz · Windows Server ·
 표본 100만 건(워밍업 10만 건 폐기), 드랍 0건입니다.

| Percentile | 지연 |
|---|---:|
| **p50** | **633.8 ns** |
| p90 | 919.3 ns |
| **p99** | **1516.6 ns (1.52 μs)** |
| p99.9 | 1629.0 ns (1.63 μs) |

메시지 1건의 서버 내 연산 비용은 중앙값 **634 ns**, p99 기준 **1.52 μs**이며, 100만 건
중 유실은 0건입니다.

---

## 2. 연산 경로 분해

컴포넌트별 비용 (Google Benchmark, median, 3회 반복, AWS 환경):

| 구간 | 단계 | 비용 |
|---|---|---:|
| Producer | 링버퍼 framing (262B 수신 write + 패킷 추출) | 24.9 ns |
| Producer | Job 할당 + 262B 본문 복사 + 방 큐 적재 (`StrandProcessor::EnqueueJob`) | 33.1 ns |
| Queue | 방 전용 MPSC 큐 push→pop | 18.9 ns |
| Queue | GlobalQueue(락프리 MPMC + 세마포어) push→pop | 37.8 ns |
| Queue | `Room::EnqueueJob` (세대검사 + push + 원자연산) | 28.0 ns |
| Pool | ObjectPool AllocBatch(16)+Free | 270.5 ns (16.9 ns/job) |
| Consumer | 브로드캐스트 패킷 조립 (고정비) | 약 26.4 ns |
| Consumer | 브로드캐스트 **수신자 1명당 한계비용** | **약 3.2 ns** |

브로드캐스트 비용은 방 인원 N에 대해 선형으로 증가합니다:

| 방 인원 | 1명 | 8명 | 32명 | 64명 |
|---|---:|---:|---:|---:|
| NotifyChat 1회 | 29.6 ns | 46.0 ns | 112.9 ns | 232.8 ns |

고정비는 약 26.4 ns이며, 여기에 수신자 1명당 3.2 ns가 더해집니다. 64명 방 전체
브로드캐스트 비용은 233 ns입니다.

---

## 3. 꼬리 지연 분석

동일 바이너리를 서로 다른 두 하드웨어(노트북 / AWS)에서 측정하여, tail latency의 원인이
알고리즘인지 실행 환경인지를 분리했습니다.

| 환경 | p50 | p99 | p99.9 | **p99.9 / p99** |
|---|---:|---:|---:|---:|
| 노트북 i7-8565U  | 347 ns | 1060 ns (1.06 μs) | 15000 ns (15.0 μs) | **14.2배** |
| AWS c6i.4xlarge  | 633.8 ns | 1516.6 ns (1.52 μs) | 1629.0 ns (1.63 μs) | **1.07배** |

노트북에서는 p99→p99.9 구간에서 지연이 14배 증가했으나, 전용 서버 코어에서는 1.07배로
좁혀졌습니다. 즉 tail latency의 원인은 코드가 아니라 전원관리·OS 스케줄링 잡음으로 판단됩니다.

## 4. 측정 신뢰도

| 항목 | 값 |
|---|---|
| 표본 수 | 100만 건 (워밍업 10만 건 폐기) |
| 유실 | 0건 (Job 풀 고갈 0, 큐 타임아웃 0) |
| 컴포넌트 변동계수(CV, real_time) | 0.02 ~ 0.25 % (Google Benchmark, 3회 반복) |
| 빌드 | MSVC v143, Release x64, `/O2` + LTCG, C++20, NDEBUG |
| 계측 방식 | `rdtsc` (QPC 기준 tick→ns 캘리브레이션), producer 코어 고정 + `HIGH_PRIORITY_CLASS` |

재현 방법:

```powershell
# 최초 1회 — 기준선 저장
Bench\run_bench.ps1 -UpdateBaseline

# 이후 — 빌드→측정→JSON 파싱→리포트 생성→기준선 대비 회귀 검사(exit code)
Bench\run_bench.ps1
```

`run_bench.ps1`은 Google Benchmark 컴포넌트 측정과 자체 `rdtsc` E2E 하네스를 순서대로
실행하고, 결과를 `results/report.md`로 자동 생성합니다. 이전 실행(baseline) 대비 10%
이상 느려진 항목이 있으면 회귀로 판정하여 0이 아닌 종료 코드를 반환합니다.

## 5. 요약 

> IOCP 채팅 서버의 연산 경로(패킷 수신 완료 → 송신 큐 적재)를 네트워크 I/O와 분리하여
> `rdtsc`로 직접 계측했습니다.
> AWS c6i.4xlarge(Xeon Platinum 8375C) 기준 **p50 634 ns,
> p99 1.52 μs**(100만 건, 유실 0건)입니다. 
> 브로드캐스트는 **수신자당 3.2 ns**로 선형 확장합니다. 동일 바이너리를 노트북과 서버 두 환경에서 교차 측정하여, 노트북에서 관측된
> tail latency(p99.9 15 μs, p99 대비 14배)가 알고리즘이 아니라 전원관리·스케줄링 잡음이었음을
> 입증했습니다(서버에서는 p99 대비 **1.07배**로 좁혀짐). 측정 전 과정은 스크립트 한
> 커맨드로 재현되며, 기준선 대비 회귀를 자동으로 감지합니다.
